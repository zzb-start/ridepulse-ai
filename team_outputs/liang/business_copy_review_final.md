## 主要问题

### 1. Strava 事件表述过强

- 位置:`报名表最终稿.md`
- 原表述:`Strava API限令致用户数据不可逆丢失`
- 判断:风险高
- 原因:当前来源更稳妥支持的是"第三方工具数据访问断裂",不宜直接升格为"不可逆丢失"
- 建议改法:改为"Strava API 调整导致第三方工具数据访问断裂,引发用户对数据控制权的担忧"

### 2. Garmin 事件不要直接写成行业普遍结论

- 位置:`报名表最终稿.md`
- 原表述:`Garmin因缓存文件损坏致数千台Edge设备全球变砖`
- 判断:中高风险
- 原因:可以作为行业案例,但不能顺势推出"行业普遍如此"或"迈金已面临同等风险"
- 建议改法:保留为单一公开案例,并明确它只是论证"骑行硬件反馈治理重要性"的背景证据

### 3. 模型评测目标与当前完成状态要分清

- 位置:`报名表最终稿.md`
- 原表述:`目标Kappa≥0.7`
- 判断:可保留
- 条件:必须明确这是试点目标,不是当前已实现结果

### 4. 李昂个人页中的骑行经历需要本人逐条确认

- 位置:`13_团队成员个人展示页.md`
- 重点表述:
  - `多年公路骑行经验`
  - `澳门路环环山路线`
  - `使用过智能骑行台`
  - `独立完成24条用户原声的骑行场景标注`
- 判断:高风险
- 原因:
  - 这些都属于可被现场追问的具体事实
  - 新增交付显示当前双人标注样本只有 20,`24条` 这一表述与现有数据口径不一致
- 建议改法:
  - 未经本人确认的骑行经历改成更稳妥的行业理解或访谈经历
  - `独立完成24条用户原声标注` 改为"参与骑行场景审核与严重度判断",或按真实样本量重写

### 5. "已完成确定性基线MVP"表述可保留,但不要偷换成完整 Agent 系统已落地

- 位置:`报名表最终稿.md`
- 判断:中风险
- 原因:当前材料可以支撑"确定性基线MVP",但完整 Agent 流水线仍应保持"方案设计 / 待验证"口径
- 建议改法:保留"已完成确定性基线MVP(无LLM调用)",同时强调完整 Agent 流水线是设计目标
